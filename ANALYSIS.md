# Анализ кода ConfigurationUSARTn

Данный документ содержит технические замечания по текущей версии исходных файлов
`ConfigurationUSARTn.c` и `ConfigurationUSARTn.h`.

Замечания разделены на две категории:
- **Подтверждено по исходникам** — дефект воспроизводится непосредственно по коду в репозитории.
- **Требует проверки по документации** — оценка зависит от reference manual конкретной ревизии GD32 и/или SDK.

---

## Подтверждённые дефекты (исправлены в данной ветке)

### 1. Неверный IRQ для USART0 в GD32F303_ ConfigUsartDMA_Rx

**Файл:** `ConfigurationUSARTn.c`  
**Расположение:** ветка `#ifdef GD32F303_`, функция `ConfigUsartDMA_Rx`, блок `if (iRQn_receiv_Uart & iRQn)`.  
**Строка до исправления:** ~327.

В `switch (usart)` для `case USART0` был назначен `USART1_IRQn` вместо `USART0_IRQn`:

```c
// было (ошибка)
case USART0: { RX_irqn = USART1_IRQn; break; }

// стало (исправлено)
case USART0: { RX_irqn = USART0_IRQn; break; }
```

При использовании `iRQn_receiv_Uart` для USART0 прерывание регистрировалось в NVIC на вектор USART1 вместо USART0. Обработчик `USART0_IRQHandler` не вызывался бы.

---

### 2. Неверный флаг в примере документации GD32F450_ ConfigUsartDMA_Rx

**Файл:** `ConfigurationUSARTn.h`  
**Расположение:** ветка `#ifdef GD32F450_`, документационный комментарий функции `ConfigUsartDMA_Rx`.  
**Строка до исправления:** ~306.

В строке `\example` использовался флаг передачи вместо флага приёма:

```c
// было (ошибка)
\example: ConfigUsartDMA_Rx (UART7, buffer_Rx, ..., iRQn_full_transmit_Dma);

// стало (исправлено)
\example: ConfigUsartDMA_Rx (UART7, buffer_Rx, ..., iRQn_full_receiv_Dma);
```

Передача `iRQn_full_transmit_Dma` (значение `0x08` из `enum confInterruptDMATransmit`) в параметр `iRQn` функции `ConfigUsartDMA_Rx`, которая работает с `enum confInterruptDMAReceiv`, не вызовет компиляционной ошибки, однако активирует неверную ветку логики прерываний приёма.

---

### 3. Дублирующий вызов usart_enable в GD32F303_ ConfigUsart

**Файл:** `ConfigurationUSARTn.c`  
**Расположение:** ветка `#ifdef GD32F303_`, функция `ConfigUsart`.  
**Строки до исправления:** 66 и 107.

```c
usart_enable(usart);          // строка 66 — первый вызов (нужен)

if (configIrqn != non) {
    // ... switch/nvic_irq_enable ...
}
usart_enable(usart);          // строка 107 — дублирующий вызов (удалён)
```

Второй вызов `usart_enable` после `nvic_irq_enable` избыточен: USART к этому моменту уже включён. Первый вызов перемещён так, чтобы охватить оба пути выполнения (с прерываниями и без).

Порядок остальных операций не изменялся.

## Замечания, требующие проверки по документации

### 4. Тип буфера в GD32F303_ DMA-функциях

**Файл:** `ConfigurationUSARTn.h` и `ConfigurationUSARTn.c`, ветка `#ifdef GD32F303_`.  
**Строки:** объявления функций `ConfigUsartDMA_Tx` и `ConfigUsartDMA_Rx` (около строк 110, 132 в .h; 133, 260 в .c).

В GD32F303_ версии буферный параметр объявлен как `uint32_t*`:

```c
void ConfigUsartDMA_Tx(enum usartDMA usart, uint32_t* buf, ...);
void ConfigUsartDMA_Rx(enum usartDMA usart, uint32_t* buf, ...);
```

При этом DMA сконфигурирован на ширину данных 8 бит (`DMA_MEMORY_WIDTH_8BIT`, `DMA_PERIPHERAL_WIDTH_8BIT`). В GD32F450_ аналогичные функции используют `uint8_t*`.

Несоответствие типа указателя и фактической ширины передачи не является однозначным ошибочным поведением: GD32F303 SDK принимает `uint32_t` в поле `memory_addr` структуры `dma_parameter_struct`. Однако использование `uint32_t*` в публичном API при 8-битной передаче может вводить пользователя в заблуждение и требует явного приведения типов на стороне вызывающего кода.

**Рекомендация:** перед изменением API проверить вызывающий код в проекте и убедиться в отсутствии зависимостей от текущей сигнатуры.  
**Статус:** не изменено, требует явного решения на уровне проекта.

### 5. Пустые IRQ-обработчики

**Файлы:** `ConfigurationUSARTn.h` (объявления), `ConfigurationUSARTn.c` (тела в комментариях).  
**Расположение:** блоки `/* ex ... */` в обоих файлах.

Библиотека объявляет обработчики прерываний USART и DMA, но не предоставляет их реализаций — тела обработчиков вынесены в комментарии как примеры. Это корректный архитектурный подход: проект должен самостоятельно определить обработчики, содержащие прикладную логику.

При этом важно:
- Если прерывание включено (через `configIrqn` или `iRQn`), но обработчик не определён в проекте, вызовется обработчик по умолчанию (обычно бесконечный цикл или сброс). Это стандартное поведение Cortex-M.
- Обработчик обязан очищать флаги прерывания, иначе МК будет бесконечно повторно входить в прерывание.
- При использовании IDLE-прерывания (`iRQn_receiv_Uart`) необходимо читать регистр данных USART для сброса флага IDLE — одного `usart_interrupt_flag_clear` недостаточно на некоторых ревизиях GD32F303.

**Статус:** описательное замечание, изменений в библиотеке не требует.

### 6. Соответствие DMA-каналов, субпериферий и IRQ

**Файл:** `ConfigurationUSARTn.c`, обе ветки.

Таблицы маппинга USART → DMA-канал → субпериферия → IRQ в коде:

**GD32F303_ (строки ~140–225, ~267–374):**
- USART0 TX: DMA0 канал 3, IRQ `DMA0_Channel3_IRQn`
- USART0 RX: DMA0 канал 4, IRQ `DMA0_Channel4_IRQn`
- USART1 TX: DMA0 канал 6, IRQ `DMA0_Channel6_IRQn`
- USART1 RX: DMA0 канал 5, IRQ `DMA0_Channel5_IRQn`
- UART3 TX: DMA1 канал 4, IRQ `DMA1_Channel3_Channel4_IRQn`
- UART3 RX: DMA1 канал 2, IRQ `DMA1_Channel2_IRQn`

**GD32F450_ (строки ~682–827, ~864–1065):**
- USART0 TX: DMA1 канал 7, субпериферия 4, IRQ `DMA1_Channel7_IRQn`
- USART0 RX: DMA1 канал 5, субпериферия 4, IRQ `DMA1_Channel5_IRQn`
- USART1 TX: DMA0 канал 6, субпериферия 4
- USART1 RX: DMA0 канал 5, субпериферия 4
- USART2 TX: DMA0 канал 3, субпериферия 4
- USART2 RX: DMA0 канал 1, субпериферия 4
- UART3 TX: DMA0 канал 4, субпериферия 4
- UART3 RX: DMA0 канал 2, субпериферия 4
- UART4 TX: DMA0 канал 7, субпериферия 4
- UART4 RX: DMA0 канал 0, субпериферия 4
- USART5 TX: DMA1 канал 6, субпериферия 5
- USART5 RX: DMA1 канал 1, субпериферия 5
- UART6 TX: DMA0 канал 1, субпериферия 5
- UART6 RX: DMA0 канал 3, субпериферия 5
- UART7 TX: DMA0 канал 0, субпериферия 5
- UART7 RX: DMA0 канал 6, субпериферия 5

Окончательно подтвердить корректность этих значений без reference manual конкретной ревизии GD32F303/GD32F450 и используемой версии SDK невозможно. Ряд каналов DMA имеет альтернативные маппинги (например, USART0 RX — каналы 2 и 5 для GD32F450, согласно комментарию в коде). Перед применением в проекте все значения должны быть сверены с документацией МК.

**Статус:** описательное замечание, требует верификации по reference manual.

## Прочие наблюдения

- В `Usart_send_buf` (строка ~1223 в .c) используется `unsigned int` вместо `uint32_t` для счётчика цикла. На 32-битной платформе Cortex-M поведение идентично, но для портируемости предпочтительнее `uint32_t`.
- Функции `ConfigUsartDMA_Tx` и `ConfigUsartDMA_Rx` выполняют `usart_disable` в начале и `usart_enable` в конце. Если USART активно используется в момент вызова, это прерывает текущую передачу/приём. Проект должен гарантировать безопасность вызова этих функций только в момент инициализации.
